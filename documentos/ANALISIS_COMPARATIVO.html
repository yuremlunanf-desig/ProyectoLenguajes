2. Introducción

Una tienda en línea recibe pedidos todos los días y cada uno debe revisarse, cobrarse correctamente y avanzar por varias etapas (preparación, envío y entrega). Hecho a mano, ese trabajo es lento y propenso a errores: un descuento mal aplicado, un IVA mal redondeado o un pedido con cantidad cero que nadie detecta a tiempo. Nuestro proyecto automatiza ese proceso y lo usa, además, para estudiar algo más amplio: cómo cambia la misma solución cuando se escribe en lenguajes distintos.

Por eso el sistema existe tres veces: en Python (interfaz Tkinter), en Java (interfaz Swing) y en JavaScript sobre Node.js (servidor Express con una página web como interfaz). Las tres leen los mismos archivos de la carpeta datos/, aplican las mismas reglas y, con los pedidos de prueba, producen exactamente el mismo total vendido: $8,360.46. Esa coincidencia es la base del estudio, porque permite comparar lenguajes y no soluciones distintas.

2.1 Objetivos

Objetivo general. Comparar la implementación de un sistema de gestión de pedidos en Python, Java y JavaScript/Node.js, evaluando tipado, ejecución, manejo de errores, estructuras de datos y concurrencia, con evidencia tomada de nuestro código y de mediciones reales. Objetivos específicos: (1) implementar las mismas reglas de negocio con arquitectura Modelo-Vista-Controlador (MVC) en los tres lenguajes; (2) construir una interfaz gráfica con login, formulario, tabla de pedidos en tiempo real y un despachador concurrente; (3) verificar la corrección con 8 pruebas unitarias por lenguaje (24 en total) y con la consistencia del total de $8,360.46; (4) medir el tiempo secuencial frente al concurrente y contar las líneas de código (LOC) reales; y (5) presentar los resultados en un tablero web comparativo (Chart.js y Mermaid.js; Chart.js contributors, s. f.; Mermaid contributors, s. f.) y en este documento.

2.2 Alcance y forma de trabajo

Incluye: versión de consola (genera resultados_metricas.json), interfaz gráfica con login contra datos/usuarios.json, formulario con vista previa de importes, tabla de pedidos, panel del despachador y el tablero servido en /dashboard. 3. Descripción del problema

Gestión manual. Los pedidos llegan como una lista de solicitudes (cliente, productos, tipo de envío) y una persona calcula los importes. El cálculo es repetitivo y sensible al redondeo: con descuentos, IVA y envío, un centavo de diferencia por pedido se acumula en el total. Los datos inválidos se descubren tarde (en nuestro archivo de prueba, PED-005 pide una webcam con cantidad 0 y debe rechazarse antes de cobrarse o enviarse) y no hay un criterio explícito de orden: se atiende lo que se vea primero.

Cuello de botella de las prioridades. Si los pedidos se atienden en el orden en que se capturan, uno urgente (prioridad ALTA con envío express) puede esperar detrás de uno de prioridad BAJA. Además, cada cambio de estado (pendiente → en proceso → enviado → entregado) depende de personas o servicios externos y tarda. Los cuatro pedidos válidos del archivo de prueba suman 9 transiciones pendientes: una tras otra, con 100 ms de espera simulada cada una, la corrida tarda cerca de 0.9 s; si los pedidos avanzan al mismo tiempo, tarda lo que el pedido más largo (3 transiciones, unos 0.3 s). La brecha crece con el número de pedidos (apartado 14).

Necesidad de interfaz gráfica y de concurrencia. Una persona no técnica no debería editar archivos JSON ni leer una consola: necesita iniciar sesión, elegir productos de una lista, ver la vista previa de los importes y recibir los errores en pantalla (messagebox, JOptionPane o una alerta web). Y como cada transición tarda, procesar la cola en el mismo hilo de la ventana la dejaría congelada: hace falta un despachador que trabaje en segundo plano con N «trabajadores», atienda primero lo urgente y avise cada cambio de estado para que la tabla se actualice en vivo (apartado 13).

4. Reglas de negocio

4.1 Fórmulas de cálculo

Las reglas se implementaron igual en los tres lenguajes. Para un pedido con líneas de precio pi y cantidad qi:

Subtotal:   S = redondear( Σ pi · qi )
Tasa de descuento:   d = 10 % si S ≥ 2,000.00;  si no, 5 % si el cliente es frecuente;  si no, 0 %
Descuento:   D = redondear( S · d )     IVA:   I = redondear( ( S − D ) · 0.16 )
Envío:   E = 50.00 (estándar)  o  120.00 (express); no causa IVA
Total:   T = S − D + I + E

La palabra clave es no encadenados: los descuentos del 10 % y del 5 % no se suman ni se aplican uno sobre otro. Gana el de monto y, solo si no aplica, se revisa el de cliente frecuente (con subtotal de $3,749.50, un cliente frecuente recibe 10 %, no 15 %; caso PED-003). El redondeo es a centavos con la regla comercial «la mitad sube» (0.005 pasa a 0.01).

Elegimos Python, Java y JavaScript con Node.js porque los tres resuelven el mismo problema con herramientas muy distintas, y esa diferencia es lo que queríamos observar. Nos dieron cuatro contrastes que se repiten a lo largo del documento:

Python representa la sintaxis breve y el tipado dinámico: se escribe menos y se ve el resultado rápido, pero varios errores quedan para el momento de ejecutar (Ramalho, 2022). Java es el extremo contrario: más texto y estructura a cambio de que el compilador detecte muchos errores antes de correr. JavaScript es el lenguaje de la web y, con Node.js, del servidor; su modelo de un solo hilo con bucle de eventos obliga a pensar la concurrencia de otra manera y nos llevó a una arquitectura distinta: cliente-servidor en lugar de una ventana de escritorio. Y cada uno resuelve distinto representar dinero, porque el punto flotante no es exacto (apartado 9).

Aparece la misma idea de encapsulamiento e inmutabilidad (frozen=True, final y List.copyOf, Object.freeze). El campo estado es la excepción, porque cambia mientras el despachador trabaja; en Java es volatile para que el cambio hecho por un hilo sea visible para los demás (Goetz et al., 2006).

7.2 Programación imperativa, funcional y dirigida por eventos

Imperativa y estructurada: las validaciones y la lectura de archivos usan secuencia, selección e iteración con salidas anticipadas mediante excepciones (se ven en los apartados 10 y 11). Funcional: las consultas sobre listas de pedidos son funciones puras que no modifican la lista recibida y devuelven una nueva, con funciones de orden superior y funciones anónimas. La misma consulta, «ordenar por prioridad y luego por antigüedad»:

def ordenar_por_prioridad(pedidos: Iterable[Pedido]) -> list[Pedido]:
    return sorted(pedidos, key=lambda p: (p.prioridad.value, p.fecha))

public static List<Pedido> ordenarPorPrioridad(List<Pedido> pedidos) {
    return pedidos.stream()
            .sorted(Comparator.comparing(Pedido::getPrioridad).thenComparing(Pedido::getFecha))
            .toList();
}

const ordenarPorPrioridad = (pedidos) =>
  [...pedidos].sort(

Python usa una tupla como clave de orden; Java encadena comparadores; JavaScript usa la tabla NIVEL_PRIORIDAD y el operador || para desempatar. Los tres copian la lista para no alterar la original. Dirigida por eventos: una interfaz espera a que ocurra algo (un clic, el aviso de que un pedido cambió de estado) y reacciona. El despachador funciona igual: en lugar de llamar a la pantalla, emite eventos tipificados (CORRIDA_INICIADA, PEDIDO_INICIADO, TRANSICION, PEDIDO_TERMINADO, CORRIDA_TERMINADA, CORRIDA_DETENIDA y ERROR) y cada interfaz los recoge a su manera (apartado 13).

8. Arquitectura de cada solución

8.1 Separación en capas Modelo-Vista-Controlador

Los tres lenguajes comparten el patrón MVC (Gamma et al., 1994; Fowler, 2002): la vista solo dibuja y muestra mensajes; el controlador recibe lo que capturó la vista, valida el formato y llama al modelo; y el modelo contiene los datos y las reglas sin saber nada de la interfaz. Así, CalculadoraPedido es la misma pieza para la consola, la ventana y el servidor web.

El dinero es la diferencia de datos más importante del proyecto. Con float o double no se puede representar 0.1 exactamente y, al sumar muchos importes, el error se vuelve visible. Python lee los precios del JSON directamente como Decimal (json.load(archivo, parse_float=Decimal); Python Software Foundation, s. f.-b), de modo que nunca pasan por float; Java usa BigDecimal con setScale(2, RoundingMode.HALF_UP) y lo construye a partir de texto (new BigDecimal("0.16"); Oracle, s. f.-a); JavaScript no tiene decimal exacto, así que convierte cada precio a centavos enteros al leerlo y solo al mostrarlo vuelve a pesos (MDN Web Docs, s. f.).

En Python, Tkinter solo permite tocar widgets desde el hilo principal (Python Software Foundation, s. f.-d); por eso el despachador deja EventoDespacho en una queue.Queue (segura entre hilos) y la ventana la vacía con after() cada 50 ms (Python Software Foundation, s. f.-a, s. f.-c). Escalabilidad. Hoy el almacén y las sesiones viven en memoria de un solo proceso: no se pueden repartir entre varios servidores sin moverlos a una base o a un almacén compartido. El polling de 500 ms hace dos consultas por segundo por navegador abierto; con muchos usuarios convendría pasar a eventos enviados por el servidor o WebSockets. Y la Tabla 17 muestra el límite que sí medimos: el pool de 16 hilos de Java frena la aceleración en ≈ 15× mientras Python y JavaScript llegan a ≈ 240× con esperas simuladas; con trabajo de CPU habría que volver a medir.

17. Conclusiones

Con evidencia de nuestro propio proyecto, llegamos a estos hallazgos: (1) la arquitectura importó más que el lenguaje: gracias a MVC, las tres versiones comparten reglas y producen el mismo total de $8,360.46, y una regla nueva se agrega en un solo método (Sommerville, 2016); (2) el tipado cambia dónde aparecen los errores: Java los detecta al compilar, Python los lanza al ejecutar y JavaScript a veces ni los lanza (a.fecha - b.fecha); (3) la concurrencia cambia cómo se avisa a la pantalla: cola con after() en Python, invokeLater en Java y polling en JavaScript; (4) el dinero exige una decisión consciente en cada lenguaje; y (5) la aceleración medida (hasta ≈ 240×) depende tanto del diseño (pool de 16 hilos) como del lenguaje.
